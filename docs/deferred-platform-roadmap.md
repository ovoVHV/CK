# CK 暂缓的平台级能力路线

更新时间：2026-07-13。状态：**已记录，当前不实施**。

## 本文范围

用户所说的“后四项”按上一轮功能清单和“后四项属于平台级能力”的语境，明确为：

1. 统一运行事件协议与硬件运行时间轴。
2. 板卡厂商认证中心。
3. 教室/实验室一致性管理。
4. 证据型 AI 诊断。

当前版本优先完成精确的可视化引脚风险图。这四项不进入当前实现范围，也不以占位 UI、模拟数据或弱化名称的方式提前宣称完成。

## 与已完成功能的边界

以下能力已经存在，是后续路线的基础，不应在执行本路线时重复开发：

- 本机四级板卡护照、推荐 Core 范围、认证失效判断和第三方包静态质量门禁。
- 上一个可用版本、工程/固件恢复、完整 FQBN、构建签名和产物哈希门禁。
- 工程体检、诊断包、默认脱敏和“为什么上次能用”差异报告。
- 断点、受限的非暂停运行轨迹、串口结构化数据、触发录制和 CSV 导出第一阶段。
- 第三方板卡/积木包的目录标准、机器可读元数据与本机导入质量报告。

这些现有能力提供的是**本机证据和静态/单机验证**。它们不等于云端厂商认证、跨机器管理、统一运行时间轴或 AI 诊断。

## 暂缓项与进入条件

### D1. 统一运行事件协议与硬件运行时间轴

目标是把上传、复位、断点、运行轨迹、探针、串口、触发、断连/重连和用户调试操作放进同一条可回放时间轴。产品名称使用“硬件运行时间轴”或“运行记录回放”，不称为源码级 Time Travel Debugger。

进入条件：

- 定义带版本的事件 Schema，包含会话 ID、事件来源、主机/设备时间、积木 ID、丢帧与截断状态。
- 明确跨串口、设备时钟回绕、复位和重连后的时间对齐规则。
- 事件采集使用有界缓冲；高速事件不得拖慢主程序或无限占用内存。
- 串口录制格式支持原始数据、解析结果和关键操作的离线回放，并完成隐私与诊断包携带策略。
- 在 AVR 小内存设备和 ESP32 系列上分别测量 Flash、RAM、吞吐、丢帧与业务时序影响。

不进入的情况：事件时间无法对齐、无法证明丢帧、只用 UI 时间伪装设备时间，或需要无界内存才能工作。

#### D1.1 串口黑匣子 `.cktrace`：已完成可行性审计，待分阶段实现

`.cktrace` 不从 CSV、曲线历史或前端文本反推原始串口数据。第一版必须在 Rust 串口读线程拿到原始字节时旁路记录，并保证录制慢盘不会阻塞串口读取。

P0 约束：

- 使用版本化容器：`manifest.json` + 长度前缀的 `events.bin`；每帧 CRC32，整段数据再校验 SHA-256。
- 记录 RX/TX 原始字节、主机单调时钟偏移、全局序号、连接/断开、用户标记与明确的 GAP 事件。
- 使用有界非阻塞队列；磁盘跟不上时写 GAP，不能静默丢弃，更不能拖慢串口读线程。
- 默认上限 64 MiB、硬上限 256 MiB；达到上限后冻结并显示“已截断”，不静默环形覆盖。
- 切换端口/波特率、上传或关闭监视器时冻结当前会话，不跨端点静默续录。
- 离线播放器不得打开串口、发送命令或重新广播全局 `serial-data`；没有板卡、Core 和端口也能播放。
- 导入拒绝未知主版本、ZIP 路径穿越、重复/加密条目、超限帧、CRC/SHA 不符和截断文件。
- 原始串口内容可能包含 Wi-Fi 密码或令牌，默认仅本机保存；诊断包默认整份排除 `.cktrace`，不伪装成已可靠脱敏。

已确认的前置修复：关闭/断开串口时最终刷新尾部缓冲；触发录制元数据使用实际已打开的端口和波特率，而不是选择器中尚未生效的值。P1 再把现有结构化绘图、触发事件和积木运行轨迹叠加到同一离线时间轴。

### D2. 板卡厂商认证中心

目标是在现有本机板卡护照之上增加厂商身份、签名证据、持续编译矩阵、真板验证记录和撤回机制。它不是把本机“已编译”标签换成“官方认证”。

进入条件：

- 发布者身份、签名密钥轮换、泄露处置、撤回列表和离线验签规则完成威胁建模。
- 有可重复的 Core/工具链/FQBN/分区配置矩阵 CI，并保存不可变构建证据。
- 真板测试记录能绑定具体芯片、实体 Flash/PSRAM、板卡修订版、测试固件和测试项目。
- 任何 Core、工具链、完整 FQBN、分区、板卡包、认证引擎或示例变化都会使相关认证失效或进入待复核。
- 明确区分厂商声明、CK 自动编译、本机真板验证和 CK/合作实验室签名认证。

不进入的情况：只有厂商自报 JSON、没有签名和撤回机制，或测试矩阵只覆盖一个默认配置。

### D3. 教室/实验室一致性管理

目标是解决同一工程在多台电脑上的 Core、工具链、驱动、库和配置漂移。第一阶段只做环境检查与 compile-only 验证，不默认批量烧录。

进入条件：

- 可移植工程胶囊能够表达依赖来源、版本、哈希、许可证和“可否重新分发”。
- 在干净 Windows/macOS 环境中验证导入结果，能明确区分“可完全复现、缺依赖、哈希不符、当前平台无工具链、仅可查看”。
- 离线安装包有完整清单、内容哈希和安全更新策略。
- 多机清单默认脱敏，不收集源码、Wi-Fi、串口内容、用户名或本机路径。
- 批量操作按设备显示结果；烧录必须逐批明确确认，失败不会自动重试到未知设备。

不进入的情况：工程胶囊尚不能在干净机器复现，或需要管理员把未知脚本直接下发到所有电脑。

### D4. 证据型 AI 诊断

目标是让 AI 只依据 CK 已采集且可引用的构建、上传、真机和运行证据提出诊断，不先做无约束的通用代码生成。

进入条件：

- FQBN、Core、工具链、构建签名、缓存证据、上传清单、真机体检、板卡护照、可用版本和运行时间轴都有稳定机器可读接口。
- 每条结论可展示引用证据、证据时间、确定程度、建议操作、修改范围和撤销点。
- 建立固定失败样本集，持续测量根因命中率、误导率、无证据结论率和人工撤销率。
- 修改工程、FQBN、Core、分区或依赖前必须向用户展示差异并获得明确确认。
- 隐私策略保证诊断包、源码、Wi-Fi、串口数据和设备标识不会默认上传。

AI 永远不得静默改 FQBN、猜测实体 Flash/PSRAM、自动降级 Core 后声称问题已解决，或在没有证据时宣称找到根因。

## 推荐进入顺序

1. **D1 统一运行事件协议与时间轴**：先统一后续验证和诊断使用的证据格式。
2. **D2 厂商认证中心**：在现有护照和质量门禁之上建立签名、撤回与持续矩阵。
3. **D3 教室/实验室一致性管理**：工程胶囊达到跨机器复现门槛后再扩展到多机。
4. **D4 证据型 AI 诊断**：最后消费前三项和现有构建链提供的稳定证据，不反过来替代底层事实。

D2 与 D3 在基础设施成熟后可以并行，但 D4 不应提前越过数据完整性与权限门禁。

## 重新排期时的完成标准

- D1：记录可离线重放，事件来源、丢帧和时间精度可解释，点击事件能稳定定位积木。
- D2：签名可验证、证书可撤回、配置变化能自动过期，厂商声明与独立验证不混淆。
- D3：干净机器复现率可统计，缺失依赖和许可证限制可解释，默认不批量烧录。
- D4：每个结论有可点击证据，无证据时明确回答“不足以判断”，所有修改可预览、可撤销。

以上完成标准达成前，只能标记为“规划中”或“实验性”，不能进入可信能力宣传口径。
