# CK Project Format v1

CK Project Format v1 是 CK 可编辑工程的单文件 JSON 合同。新建工程使用 `.ck` 扩展名；历史 `.maker` 和没有版本字段的 `.ck` 仍可读取，并在下一次显式保存时进行无代码执行的数据迁移。

规范 Schema：[`schemas/ck-project.schema.json`](schemas/ck-project.schema.json)

## 1. 格式身份

v1 工程的三个保留字段为：

```json
{
  "format": "ck-project",
  "schema_version": 1,
  "migration_version": 1
}
```

- `format` 标识文件属于可编辑 CK 工程，而不是 `project.ckpkg` 提交容器、诊断包或扩展包。
- `schema_version` 表示公开 JSON 合同版本。
- `migration_version` 表示已应用的数据迁移级别。它不代表应用版本，也不允许触发脚本。

CK 1.0 仅支持完整身份 `format = "ck-project"`、`schema_version = 1`、`migration_version = 1`。三个字段必须同时出现；值为 `0`、高于当前版本、类型错误或只出现其中一部分都会在读取、覆盖保存和重命名前明确拒绝。历史 v0 的识别条件是三个身份字段全部缺失，而不是显式写入版本 `0`。

## 2. 最小工程

```json
{
  "format": "ck-project",
  "schema_version": 1,
  "migration_version": 1,
  "name": "blink",
  "board": "arduino:avr:uno",
  "board_package_id": "arduino:avr:uno",
  "created_at": "2026-07-16T06:00:00Z",
  "xml": "<xml></xml>",
  "code": "void setup() {}\nvoid loop() {}",
  "options": "{}"
}
```

`xml` 是可编辑积木工作区。`code` 是最近一次生成的源码副本，便于携带和检查，但不是构建历史。`options` 在 v1 中继续沿用“JSON 对象编码为字符串”的旧表示，避免破坏现有工程；未来若改变其类型，必须提升 `schema_version`。

`board` 保存板卡目标/FQBN base，`options` 保存显式菜单选择；两者共同重建实际完整 FQBN。v1 不额外复制一份可能与 `options` 漂移的 effective FQBN。`board_package_id` 保存具体 CK 板卡包身份，因为两个第三方板卡包可能共享同一个 FQBN。

## 3. v0 到 v1 的迁移

“v0”指历史 `.maker` 或 `.ck` 单文件 JSON：其工程字段有效，但没有三个格式身份字段。迁移遵守以下规则：

1. 只解析 JSON 数据，不执行积木生成器、第三方 JavaScript、构建工具或安装钩子。
2. 在内存中加入 `format`、`schema_version` 和 `migration_version`，值均按本规范固定。
3. `name`、`board`、`xml`、`code`、`options`、`ck_block_packages` 及未知字段保持原值。
4. 只读打开不改写磁盘；用户下一次显式保存时才落盘升级。
5. `.maker` 保存后仍为 `.maker`，不会擅自改扩展名。新建工程才默认使用 `.ck`。

迁移是单步纯数据变换，重复应用结果相同。格式元数据是保留键；旧文件若已使用同名字段但类型或值不合法，会被拒绝而不是猜测。

历史文档也必须至少提供非空字符串 `name`、非空字符串 `board` 和字符串 `xml`。版本化 v1 使用同一严格字段检查；缺少工作区或把 `xml` 写成对象/数组时必须拒绝打开和覆盖，不能把损坏数据当成空工程。

## 4. 前向兼容和未知字段

Schema 使用 `additionalProperties: true`。CK 保存现有单文件工程时先读取完整 JSON 对象，只替换当前操作明确修改的字段，并保留未知字段及其嵌套数据。扩展字段不得依赖键顺序或空白格式，因为保存会重新进行规范化 JSON 序列化。

“另存为”以当前源工程的完整 JSON 对象为基底：另存到新路径时保留源工程的未知字段；覆盖另一已有文件时，目标文件只用于格式/未来版本安全检查，其未知字段不得混入源工程。恢复稿导出等没有源单文件的流程从干净 v1 对象开始，不读取目标文件作为内容基底。

接受未知字段不等于信任其行为。CK Project Format 是数据容器；项目中的未知数据不会自动获得代码执行权限。第三方积木的运行边界仍由扩展包质量门禁和声明式运行规则决定。

“另存为”以当前源工程完整 JSON 为基底，再替换用户本次明确修改的字段；目标文件即使存在也只能接受格式/未来版本保护检查，绝不能把目标的未知字段混入源工程。没有源文件的恢复稿另存为从干净 v1 文档开始，避免继承同名旧目标的扩展数据。

## 5. 原子保存

`.ck` 和 `.maker` 单文件保存采用以下流程：

1. 在目标文件同一目录创建唯一临时文件；
2. 写入完整 UTF-8 JSON 并同步临时文件；
3. 使用操作系统的原子替换能力替换目标文件；
4. 失败时清理临时文件，原目标不通过“先截断再写入”的方式更新。

同目录是合同的一部分，避免跨文件系统移动导致原子性失效。Windows 使用带 `REPLACE_EXISTING` 和 `WRITE_THROUGH` 的系统替换；类 Unix 系统使用同文件系统 `rename`，并同步目录项。

单文件重命名只接受安全的单个文件名，不接受绝对路径、`..`、目录分隔符、控制字符或 Windows 保留设备名。重命名先原子发布一份内部 `name` 已更新的完整新文件，再删除旧文件；若进程在两步间退出，最坏结果是两个各自完整的工程副本，不会留下“新文件名配旧内部名称”的半更新文件。

## 6. 明确不嵌入的内容

以下内容不属于 CK Project Format v1 的默认工程正文：

- 工程检查点和崩溃恢复快照；
- 编译历史、缓存对象和编译日志；
- 上一个可用版本的固件段、上传清单和真机证据；
- 质量报告、诊断包和课程验收报告。

它们由 CK 的本地证据存储、旁路缓存或独立导出格式管理。这样复制 `.ck` 不会意外携带大量设备信息，也不会让工程编辑操作改写审计证据。

## 7. 与其他 CK 格式的边界

| 格式 | 用途 | 是否是可编辑工程正文 |
| --- | --- | --- |
| `.ck` | CK Project Format v1 单文件工程 | 是 |
| `.maker` | 可继续读取/保存的历史单文件扩展名 | 是，保存时迁移内容版本 |
| `project.ckpkg` | 工程提交与验收容器 | 否 |
| 扩展 ZIP | 板卡、积木或 Arduino 库导入包 | 否 |
| 诊断 ZIP | 脱敏环境、日志和故障证据 | 否 |

## 8. 实现与验证要求

实现至少应回归：

- 新建工程扩展名和三个格式字段；
- 无版本 `.ck` 与 `.maker` 的只读兼容和保存迁移；
- 未知字段在普通保存与“另存为覆盖”中的保留；
- 另存为保留源未知字段且不混入目标未知字段；
- 缺失/错类型工作区、部分格式身份和零版本必须 fail-closed；
- 未来 schema/migration 版本在写入前拒绝；
- 同目录原子替换不留下临时文件；
- Schema 是有效 JSON，且固定格式身份与版本常量。
