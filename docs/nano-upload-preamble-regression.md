# Nano 上传前准备：整数宏与重复前端开销

2026-11-27，两份 1.0.60 的 Nano 上传日志显示：首次准备耗时 8.665 秒，改码后 7.279 秒，其中官方前端分别占 4.937 和 4.894 秒。改码后只编了一个对象。日志指向预处理指令，没有源码，不能确定具体是哪一条。1.0.61 的 `src/` 相比 1.0.60 只变更了版本号。

以前，即使主程序开头只定义一个引脚整数常量，CK 也会在每次改码后重新调用官方前端。候选修复允许形如 `#define OUTPUT_PIN 13` 的前置对象宏；名称、值及相对于头文件的顺序都参与依赖发现判断。常量变化会重新检查依赖。条件编译、宏形式的 include 和函数宏保留官方处理。新日志为不支持的预处理指令报告类别和行号，不附带自定义宏名、路径或代码。

## 本机对照

同一份已发行的 1.0.61 Windows 桌面程序，普通用户，Nano ATmega328P、Arduino AVR Core 1.8.8、16 jobs。对照直接使用公开安装包内的原版引擎；修复组仅替换引擎源码。顺序为原版、修复、修复、原版。每组启动新的桌面进程和工程会话。没有清空系统磁盘缓存，“首次”指该工程的第一笔请求。

下表是两次各自的实测值，单位为秒。计时从桌面后端收到上传请求，到编译、固件清单与工具链检查完成；不含前端点击和串口传输。

| 场景 | 已发行 1.0.61 | 修复后 |
| --- | ---: | ---: |
| 新工程，含引脚常量 | 11.183 / 6.531 | 4.139 / 4.093 |
| 只改 `delay(137)` 为 `delay(291)` | 4.663 / 4.873 | 1.845 / 1.707 |
| 引脚从 13 改到 12 | 5.153 / 4.350 | 1.940 / 1.822 |
| 源码完全相同 | 0.926 / 1.067 | 1.471 / 0.993 |
| 切换到含 `#if` 的新源码 | 4.514 / 5.035 | 5.657 / 6.096 |

改 `delay` 的两次候选运行都复用了发现结果和函数原型，重新编译一个对象，沿用 25 个对象。改引脚的两次运行均重新执行发现，生成的 HEX 随之变化。完全相同的工程没有稳定提速。最后一行两组均调用官方前端，但候选从原生路径切到官方路径；两次都比原版慢，不计入提升。两轮数据不能估算 P95，亦不能替代提交者工程复测。

## 复验方法

用 `scripts/Start-Preview.ps1` 对两套引擎运行 `tests/desktop-avr-preamble.mjs`；分别设 `CK_PREAMBLE_ENGINE=stock` 和 `candidate`。脚本调用 `observe_upload_preparation`，检查实际 HEX、编译任务数、复用决定以及上传校验结果，并在串口传输前停止。

四场桌面运行分别产生一个证据目录。在性能测试结束后，用以下命令独立编译与核对（每个不同的源码均使用新的官方 CLI 构建目录）：

```text
runtime/node.exe tests/desktop-avr-preamble.mjs --verify-official <config.json> <stock1-run> <candidate1-run> <candidate2-run> <stock2-run>
```

本次使用 Arduino CLI 1.4.1；四份不同源码、20 次桌面结果的应用 HEX 全部与对应官方构建逐字节一致。未执行真机烧录。

## 工程自带 PCA9685 驱动

同机 Nano，在同名 `.ck` 文件夹内放入 FaBo 官方 `FaBoPWM-PCA9685-Library` 的 `src/FaBoPWM_PCA9685.{cpp,h}`（提交 `fe0946e8cbd831c46573625191699ce784b7d957`）。运行上游 `example/servo/servo.ino`，只调整主程序头文件路径为 `#include "src/FaBoPWM_PCA9685.h"`，驱动同目录内的引用仍写裸文件名。独立官方 CLI 在仅有这两个 `src` 文件、没有全局安装该库时，从工程根部写裸文件名会报头文件找不到。测试没有更改搜索顺序，也没有安装全局 FaBo 库。每次桌面运行都检查实收的两个工程文件摘要以及选中的 `Wire`。

同样的上传准备计时（秒），以下为两次原版与两次最终候选。各行是同一会话内依次进行的操作。

| 场景 | 1.0.61 | 候选 |
| --- | ---: | ---: |
| 工程首次，直接 include | 4.793 / 5.174 | 4.498 / 4.515 |
| 在示例循环中只改等待值 | 2.078 / 2.030 | 1.857 / 1.823 |
| 只改驱动 `.cpp` 的等待值 | 2.289 / 2.329 | 2.243 / 2.319 |
| 改 `.h` 的默认 I²C 地址 | 2.336 / 2.253 | 2.321 / 2.338 |
| 完全相同 | 1.039 / 0.950 | 1.034 / 1.004 |
| 主程序新增通道整数宏并使用它 | 6.055 / 5.868 | 2.379 / 2.181 |
| 保留通道宏，只改等待值 | 4.880 / 5.649 | 1.806 / 1.776 |

库本身不会导致回退。无宏示例的比较循环以往会导致改等待值时重复调用预处理器和 ctags。候选复用已观察到的转换：仅在上下文满足限制且只有独立等待调用中的整数字面量变化时使用。相同会话下的两个主程序等待值用例均只重编主程序；驱动实现变更只重编驱动，头文件变更则重编主程序和驱动，后两种没有稳定的耗时改善。通道宏是额外的受控变量，不是上游示例自带的内容。以上不是提交者的原始工程，不能反推其出问题的行。

复验：设置 `CK_FABO_CHECKOUT` 指向上述提交，按前文方法将 harness 换为 `tests/desktop-avr-project-driver.mjs`。再用同一脚本的 `--verify-official <config.json> <run-dir> ...` 独立干净编译每个场景，逐字节核对各次桌面准备的应用 HEX。

## 用户提供主程序和八个同级文件后的复测

按给出的代码重建 `.ck`，将三个 `.cpp` 和五个 `.h` 逐字节复制到与 `.ck` 同一层，不修改 include，不安装全局驱动。Nano ATmega328P、AVR Core 1.8.8、16 jobs，对照仍用发行版 1.0.61。同机桌面上传准备，原版 / 候选 / 候选 / 原版，每轮独立进程、独立工程会话，不含串口烧录。每个工程累计执行编辑，每步都核对传入引擎的成员摘要。

| 小车工程（秒） | 1.0.61，两轮 | 候选，两轮 |
| --- | ---: | ---: |
| 首次 | 9.268 / 7.108 | 5.035 / 4.666 |
| 转弯时间常量 320 → 340 | 5.130 / 5.097 | 2.090 / 2.077 |
| 方法调用中的频率参数 47 → 49 | 5.013 / 4.939 | 1.982 / 1.970 |
| 原样重复 | 1.006 / 1.084 | 0.971 / 1.031 |
| 驱动头文件默认地址变化 | 5.038 / 4.886 | 2.366 / 2.377 |
| 驱动实现变化 | 5.489 / 4.956 | 2.352 / 2.905 |
| 未用到的循迹实现变化 | 5.143 / 4.804 | 2.263 / 2.647 |
| 引脚宏变更 | 4.733 / 4.991 | 2.396 / 2.492 |

原版对这份主程序的整数宏调用了官方前端。候选对主程序两种普通编辑都只编一个对象；多个辅助函数仍使用真实原型处理。地址变化时主程序和驱动均重编；更改未用到的循迹实现时只重编该对象，最终固件不变。首次依赖发现现在也能编译工程的 C++ 成员；是否采用该对象仍取决于最终编译命令、包含路径、实际依赖和输出的完整验证。不以库名、工程名或板卡型号选择此优化。

对照工程是串口输出模拟量的独立多文件程序，没有 I²C、电机或等待函数。改串口配置常量：4.490 / 4.393 秒 → 1.884 / 1.801 秒；改调用：4.375 / 4.404 秒 → 1.673 / 1.792 秒。两组结果均不构成所有板卡的 P95 验收。

使用 `scripts/Start-Preview.ps1` 启动 `tests/desktop-project-upload-edits.mjs` 可直接复跑公开的模拟量样例。可选 `CK_EDIT_FIXTURE` 指定含 `main.ino`、成员和 `edits.json` 的其他工程测试输入。结束后用同一脚本的 `--verify-official <config.json> <run-dir> ...` 用 Arduino CLI 干净编译并比对各场景 HEX。用户提供的源码不随仓库分发。

## ESP32 多文件复验

2026-11-27，Windows 普通用户，同一份 1.0.61 桌面 EXE、16 jobs、ESP32 Core 3.3.6-cn。独立样例 `tests/fixtures/upload-edits/network` 的 `.ino` 引用工程根部的头文件，`src/NetworkTask.cpp` 内引用 `WiFi.h`。每次启动后连续准备三次：首次、只改 `.ino` 传给驱动的名称、原样重复。整个会话中驱动文件只写入一次。每次都验证了工程成员的 SHA-256、应用 BIN 和上传清单，未连接设备。改码后实际 BIN 含新名称且不含旧名称，原样重复的 BIN 与上一次逐字节相同。

同盘（C 盘工作目录）桌面上传准备时间，单位秒，不含点击、串口传输；首次指新的工程会话，不清空 Windows 文件缓存。

| 板卡与引擎 | 首次 | 只改主程序 | 原样重复 |
| --- | ---: | ---: | ---: |
| S3，发行版 1.0.61 | 81.364 | 43.792 | 3.106 |
| S3，最终候选 | 59.556 | 14.612 | 3.182 |
| C3，最终候选 | 76.966 | 12.143 | 3.347 |

两个候选板卡的改码收据均为发现 GCC 0、原型 GCC 0、ctags 0、编译 GCC 1，仅重编 `sketch.ino.cpp.o`，沿用 71 个对象；原样重复未执行编译、链接或镜像生成。较早的 E 盘对照为 S3 发行版 95.013 / 48.991 / 3.286 秒、修正字符串判断前的候选 97.647 / 21.660 / 3.672 秒。首次耗时波动大，不能当作稳定提升或 P95；C3 未运行发行版对照。没有测其他 ESP 板卡或核心版本。

此前原型判断把普通字符串结尾的 `R"` 误判为原始字符串，导致第二次编译额外调用预处理器和 ctags；现在复用已有的词法判断，对真正的原始字符串仍走原流程。测试时设置 `CK_EDIT_FQBN` 为 `esp32:esp32:esp32s3` 或 `esp32:esp32:esp32c3`，`CK_EDIT_FIXTURE` 为样例绝对路径；候选另设 `CK_EDIT_EXPECT_REUSE=1` 以强制断言实际复用，不把这些耗时作为测试阈值。
