# alpha.57 首编调查和 alpha.58 回退范围

对照的是正式 Windows 安装包，板卡为 ESP32-S3，Core 为 `3.3.6-cn`，WiFi 仅作为测试输入。单位：秒；按钮耗时计到可以再次点击。每轮独立桌面进程、空构建目录、8 个任务；未清 Windows 文件缓存。每轮真实编译 71 个对象。下表为同机样本，不是 P95。

| 版本和条件 | 按钮总计 | 按钮进出后端 | 发现和并行编译 | 链接 |
|---|---:|---:|---:|---:|
| .55 首次强校验 | 66.21 | 0.11 | 36.52 | 7.41 |
| .56 首次强校验 | 64.17 | 0.23 | 36.31 | 7.34 |
| .57 首次强校验 | 74.40 | 0.06 | 43.81 | 8.31 |
| .55 已有校验记录，完整重建 | 57.50 | 0.11 | 35.98 | 7.33 |
| .56 已有校验记录，完整重建 | 54.96 | 0.28 | 36.74 | 7.78 |
| .57 已有校验记录，完整重建 | 63.75 | 0.09 | 43.66 | 7.75 |
| .55 另一次首次强校验 | 73.13 | 0.12 | 43.10 | 7.80 |

首组 .57 比 .55 首编多 8.19 秒，发现和并行编译多 7.29 秒。两版使用相同核心和实际工具链；不是退回兼容后端，也没有少开加速。`.56 → .57` 的 `src/` 只改版本号，两个正式包的 `engine.mjs`、原生资产助手、Node、Ninja 和 Arduino CLI 哈希相同。桌面编译生命周期改过，但该组多出来的时间发生在后端工作期间。`.55` 单独复跑也能出现相近的阶段耗时，现有数据不能把差额归因于某一提交、杀毒软件或某个库。

Uno AVR 1.8.8 同一套按钮测试中，.55 首编 8.14 / 6.15 秒，.57 为 6.66 / 5.38 秒；该机没有复现与 S3 相同的回退，不据此否定其他用户的记录。

发布环节存在可确认的缺口：.57 的发布说明明确说明验证了功能正确性，但没有复测编译速度。之前的 30 次改码 P95 也不能代替空构建目录的首编验收。后续替换 .55 调度前，应对实际交付安装包、Uno 和 S3 CN 分别跑首编和改码，保留每轮计时、任务数和固件证据；不能用原样命中或普通版 ESP32 Core 代替。

alpha.58 从 `v9.1.0-alpha.55`（`0f04f11`）构建。ESP32 `merge.inputs` 按配方工作目录解析路径，保证当前应用与分区进入合并镜像。另在 .58 安装包预验收中复现了深目录下的独立故障：S3 首编成功，改码时 Ninja 对 `.commands` 中的长绝对路径报错。修正图文件中长路径的拼写，实际命令、文件内容及校验保持不变。不把这个编译失败当作解释前述成功首编耗时差异的原因。版本身份、收据校验和更新清单都使用真实 .58 版本号。
