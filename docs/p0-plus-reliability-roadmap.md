更新时间：2026-07-13。状态：上传优化、Flash/RAM 资源预算、可操作错误卡片、精确引脚风险图、非暂停运行轨迹、串口触发录制、本地工程检查点和“上一个可用版本”均已接入原生软件；真机断言继续按安全门禁推进。

## 本轮结论

在不引入 AI、生态平台或统一 IR 的前提下，近期功能按“看得见、测得出、防得住、恢复得了”推进。本轮优先级如下：

1. **确定性编译保护已完成第一阶段**：Flash/RAM、错误卡片和引脚体检都只根据能够证明的信息行动；不确定内容保留为提示或原始日志。
2. **串口触发录制已完成第一阶段**：使用固定容量环形缓冲和明确的数值条件，支持触发前后窗口与 CSV 导出，不控制或暂停开发板。
3. **本地工程检查点已完成第一阶段**：复用正式 Blockly JSON，在编译、上传、恢复和主动放弃未保存修改前自动保护，并支持手动保存当前状态；恢复或放弃修改前保护失败时拒绝覆盖当前工作区。
4. **运行轨迹与采样覆盖率已完成第一阶段**：使用独立轨迹固件非暂停采样，固件端和桌面端都有固定容量、频率和刷新门禁；界面明确只统计采样命中，不宣称精确执行次数。
5. **“上一个可用版本”已完成整合，真机断言仍暂缓**：可用版本保存工程、锁文件、构建配置和完整固件产物，恢复固件前重新执行芯片、Flash、FQBN、分区、地址和哈希门禁；真机断言仍需先解决无副作用求值与失败后的硬件安全状态。

本记录不是完成承诺。若原生软件回归出现新增阻断性问题，应撤回对应功能并保留测试、失败原因和重新进入条件。

### 推荐数据流

```text
Blockly 工作区
  -> arduinoGenerator.workspaceToCode
  -> generatedCode + lineToBlockMap
  -> handleCompileAndUpload
  -> Tauri compile_sketch / upload_sketch
  -> 成功：构建体检 + 资源预算
  -> 失败：完整日志 + analyzeCompileIssues
       -> BuildIssueCards
       -> 用户明确点击动作
       -> 库搜索 / 扫描串口 / BOOT 帮助 / 资源面板 / 板卡设置
```

当前接线只在 `handleCompileAndUpload` 的失败路径分析一次“本次会话完整日志”，并在下一次编译开始时清空。回归时必须保持这一点，不能改为逐行流式创建卡片，否则半条日志可能产生闪烁或重复判断。

### 误报控制

- 缺头文件只匹配 `fatal error ... .h ... No such file` 或 `file not found`。操作是“按头文件搜索”，不自动安装排名第一的库。
- 串口错误必须包含明确的 open/port/device 错误，或 OS 错误与 COM、`/dev/tty`、serial 上下文同时出现。普通文件的 `Access is denied` 不归类为串口问题。
- ESP BOOT 帮助只在 FQBN/日志确认 ESP 系列且出现明确握手错误时出现。若串口本身打不开，先只显示串口卡片。
- 固件过大只匹配链接器 overflow、`Sketch too big` 等失败签名。正常的 `Sketch uses 73%` 不算错误。
- 环境变化只描述事实，明确写“不一定是错误原因”，不能自动清缓存。
- 未知 C/C++ 语法、模板、第三方核心错误保持原日志和现有积木定位，不生成泛化按钮。

## 精确引脚风险图与编译前体检：结构契约已接入

### 当前实现

- `apps/desktop/src/services/pin_preflight.ts` 是不依赖 AI 的纯函数分析服务。内置积木使用显式 block type 规则；v2 第三方积木可通过机器清单声明 `kind`、`access`、`sharing` 和所需 `capabilities`，不依赖字段名猜测。
- 风险图展示当前板卡包清单中**声明的全部引脚**，包括其中尚未占用的引脚；可搜索 GPIO 值、`D2`/`PA5` 等别名、能力、保留资源、风险代码和使用积木，并按全部、已占用、有风险、未占用筛选。当前 Schema 不能证明发布者没有漏列物理引脚，因此界面不会把清单外的世界宣称为完整或安全。
- 板卡包 `pins` 已支持 `aliases`、`capabilities`、`risks`、`reserved_by`、`sharing`、`connector`、`source` 和 `evidence`。`risks.when.options` 可让 USB/JTAG 等风险只在对应完整 FQBN 菜单配置下生效；`risks.when.features` 可让经典 ESP32 的 ADC2/WiFi 等工程特征风险只在实际使用对应功能时生效。
- 第三方板卡包身份与 Arduino 编译 FQBN 分离。同一官方 FQBN 下存在多个自制板时，工作区、保存工程、库解析和引脚体检均按精确包 ID 选中该板自己的引脚目录，不再回退借用同 FQBN 的内置板卡数据。
- 精确包 ID 同时贯穿积木加载、库管理器导入、编译与上传。板卡包缺失、内容被改动、质量报告失效或 Core 门禁未就绪时只允许查看工程，不能借同 FQBN 的另一块板继续构建。
- 板卡包未声明任何可用引脚时，积木下拉显示不可生成源码的“未声明引脚”占位；该占位在生成器和编译前体检两层都会被拦截，永远不能进入 C/C++。
- 能力字段缺失表示“未知”，不表示支持。普通 `digital`/GPIO 声明不会被推断成外部中断、ADC、PWM 或总线能力。
- 编译或上传前仍同步重算体检；界面中的积木可点击定位。变量和其他动态表达式继续标记为“运行时决定”，不会据此猜测冲突。
- 同一积木内部可证明的冲突继续阻断，例如 Shift 的 data/clock 相同、串口 RX/TX 相同。跨积木复用则结合 `sharing`、角色和证据判断；共享总线不会仅因复用同一引脚被误判。
- 只有 CK 可验证的确定性事实可以成为阻断项。发布者把风险标成 `blocker` 时，若缺少可验证证据，软件会降为警告；输入未连接、别名不明或能力未声明也只显示未知/提示。

### 证据与显示边界

- Schema 证明的是“声明结构合法”，不自动证明板厂声明真实。能力、保留脚和电气风险仍应引用具体 Core、原理图、数据手册或真板报告；逐引脚的 `source`/`evidence` 原样保留在 `board.json`，整个包的内容 SHA-256 进入质量报告。当前静态门禁只校验这些证据声明的字段形状，尚不解引用外部资料，也不独立证明发布者填写的引用或逐项哈希真实，因此界面必须把它标为发布者声明而非 CK 复验事实。
- 缺少 `connector` 物理位置时只显示目录图，并明确提示“未声明物理坐标”；不能根据 GPIO 数字猜测排针顺序。
- 内置的通用 ESP32/C3/C5/C6/S3 编译目标目前仍有一部分只是基础 Core 引脚目录，并不自动等于某块商品板的原理图。没有版本化原理图/Core 证据的风险保持灰色未知；第三方板厂若需要精确到自家丝印和板载资源，必须随包提供自己的别名、连接器、保留资源、风险与证据。
- 未声明引脚角色的旧第三方积木继续保持兼容，但不会因为字段名包含 `PIN` 就产生高置信风险结论。声明 v2 角色后才参与能力和共享规则。
- `apps/desktop/src/types/agent.ts` 中早期的 Agent pin 类型不是事实来源；后续 AI 工具必须复用同一 `pin_preflight.ts` 报告和包质量证据，不能另建一套漂移规则。

### 后续验证门禁

1. 为 Uno、Nano、Mega、ESP32-C3/C5/C6/S3、ESP8266 等内置目标持续维护与具体 Core 版本绑定的别名和能力证据，版本变化后使旧证据过期，而不是静默沿用。
2. 板厂发布包必须用自己的丝印、连接器和原理图事实替换示例数据；CK 不要求官方逐块手写规则，但错误或互相矛盾的精确元数据会阻止导入。
3. 真实工程误报率应低于 1%，所有不确定结果只显示提示、不阻断编译；只有可重现的确定性规则才允许升级为 blocker。
4. AI 检索、文档展示和编译前 UI 必须消费同一份机器可读引脚目录和同一纯函数报告，避免两套规则漂移。

## 运行轨迹与采样覆盖率：第一阶段已完成

### 当前实现

- `Workspace` 的“运行轨迹”入口会生成、编译并上传独立轨迹固件。普通上传、断点调试上传和轨迹上传是三条明确分开的路径，轨迹运行时不会进入断点暂停。
- 当前支持 ESP32、ESP8266 和 Arduino AVR；启动前必须选择串口。程序若主动读取主 `Serial`，软件会拒绝开始轨迹，避免用户代码吞掉 ATTACH/STOP 命令。
- 轨迹固件默认最多登记 64 个可执行积木，超出的积木会明确提示并跳过，不在小内存设备上建立无限 block ID 表。
- 固件默认每经过 4 个检查点才进行一次普通采样；首次命中的积木仍可立即产生 first-hit 轨迹。所有轨迹帧还共享 40 ms 全局最小发送间隔，因此固件最多约 25 帧/秒。
- 桌面端使用固定容量聚合器，保留每个已登记积木的采样命中、首次/最近命中和上一个采样积木，并以固定环保存最近 32 条采样路径；未知积木或超限帧会被保护性丢弃。
- Blockly 覆盖样式、覆盖比例、最近路径和积木定位均已接入；结束轨迹会等待设备确认并清除本地覆盖样式，但不会自动把板上固件刷回普通版本。
- 第一阶段通过 TypeScript 检查、63 项前端服务测试和生产构建。

### 必须保持的解释边界

- 界面中的“次数”是采样帧命中次数，不是积木的精确执行次数。高速循环中，一个积木可能执行多次但只产生一条采样帧。
- “采样覆盖率”只表示已登记积木中哪些至少被采样命中过；未命中不等于代码绝对没有执行。
- 积木间时间来自开发板两个采样点的 `micros()` 差值，其中包含用户代码、采样门禁和轨迹运行时开销，不能作为无干扰性能基准。
- 轨迹固件会占用主串口并带来少量运行开销。正式部署或需要恢复普通运行时序时，用户必须执行“普通上传”。

### 后续阶段门禁

1. 若要支持用户选择特定流程，必须保持未选流程完全不插桩，并为工程修改后的 block ID 变化建立回归。
2. 若要提高上限或帧率，必须分别在 Nano、Uno、Mega、ESP32-C3/C5/S3 和 ESP8266 上重新测量 RAM、Flash、串口丢帧及业务时序偏移。
3. 若要显示更精确的执行次数或性能数据，必须设计独立的设备侧聚合协议；不能把当前采样统计改名冒充精确覆盖率。
4. 轨迹与用户串口共存、第二硬件串口和离线缓冲只能在协议隔离与溢出行为可证明后加入。

## 真机断言与测试报告

### 价值

它把 CK 从“生成程序”推进到“证明程序在真机上工作”，但比普通积木更接近测试运行时和协议系统。

### 主要风险

- `2 秒内收到消息` 等断言需要明确时钟、串口/总线来源和超时语义。
- 断言表达式可能有副作用，重复求值会改变程序行为。
- 测试失败后直接暂停可能触发执行器或电机停在危险状态。
- Nano 的错误文本和测试记录不能大量驻留 RAM。
- 重复 100 次需要确定 setup 重置、状态隔离和看门狗策略。

### 推荐顺序

1. 先做无副作用的 `断言 布尔条件` 与 `测试通过/失败`，失败只上报，不自动改变输出。
2. 使用现有 block token 和串口会话 ID，报告保存 block ID、次数、首次失败时间和简短值摘要。
3. 错误字符串放 Flash，主机端负责生成完整中文报告。
4. 延时断言、消息断言和重复测试在基础断言真板稳定后再加入。
5. 安全输出/故障收尾必须由用户显式配置，不能假设所有硬件都适合直接停止。

- 用户可执行“与可用版本比较”“恢复工程”“恢复固件”和“完整恢复”。比较报告把代码、依赖、Core、工具链、菜单选项、分区和真机变化翻译成可读差异，不只显示文件哈希。
- 恢复工程不会自动烧录；恢复固件不会覆盖当前积木。完整恢复先恢复工程和配置，再使用保存的完整产物清单烧录。
- ESP32 保存 bootloader、partition、boot app、应用及全部 flash offsets/args，不把单个应用 `.bin` 冒充完整恢复包；Windows 长路径烧录使用受控短路径暂存并在结束后清理。
- 恢复固件前重新检查当前芯片族、实体 Flash、完整 FQBN、分区、烧录地址、必需产物和 SHA-256。缺少任何必要证据或产物时拒绝恢复，不能因“恢复”绕过上传安全门禁。

### 必须保持的解释边界

- “编译成功”不会创建可用版本；当前基线至少要求上传与产物门禁成功。它证明的是 CK 已成功构建和写入，不自动证明用户业务行为已经长期稳定。
- 固件可能包含 Wi-Fi 密钥等敏感信息，版本目录只保存在本机受控位置，诊断包和云端流程不得默认携带固件或源码。
- Core、工具链、完整 FQBN、分区或真机发生变化时必须展示差异并重新门禁，不能因为旧版本曾经成功就静默信任当前环境。

## 串口触发录制：第一阶段已完成

### 当前实现

- 只对串口绘图器已经解析出的结构化数值通道工作，不重新从普通日志文本中猜测数字含义。
- 用户明确选择通道、`>`、`>=`、`<`、`<=`、`==`、`!=` 条件和阈值，再设置触发前后时间窗。
- `SerialTriggerRecorder` 使用固定容量环形缓冲；每侧时间窗最多 30 秒，单次最多 5000 条记录。达到上限会冻结并标记为截断，不允许内存无限增长。
- 触发后仍记录其他结构化通道，即使被观察通道在某一行缺失，也能保留同一时间窗的关联数据。
- 支持立即冻结、结束、重新布防与独立 CSV 导出。导出包含触发规则、实际触发值、相对时间、串口、波特率和录制期间输入积压丢弃数。

### 第一阶段限制

- “冻结录制”只固定本地捕获窗口，实时曲线和开发板程序继续运行；本阶段不会自动暂停设备或发送串口控制命令。
- 时间窗按 CK 收到数据的主机时间计算，不是开发板硬实时采样时钟。
- 本阶段没有在曲线上绘制持久事件注释，也没有多条件组合、滞回或设备侧触发。
- 串口输入速率超过界面处理能力时仍可能丢弃积压；导出会记录丢弃数量，不能把缺样数据误认为连续采样。

## 本地工程检查点：第一阶段已完成

### 当前实现

- 直接保存 `Blockly.serialization.workspaces.save()` 返回的完整 JSON，并同时保存生成代码、板卡、板卡选项、积木数和原因；不另造简化快照格式。
- 自定义 serializer、变量、过程、断点和第三方 mutator 状态保持为不透明 JSON；恢复仍依赖对应第三方积木包已经安装。
- 自动创建时机为编译前、上传前、恢复前，以及用户明确放弃未保存修改并离开工程前；“工程检查点”窗口也可手动保存当前状态。编译/上传前保存失败会在日志中警告但继续操作，恢复或放弃修改前保护失败则拒绝覆盖当前工作区。
- 桌面后端先写临时文件并同步，再以唯一文件名原子落盘。每工程最多保留最近 20 个，单个最多 5 MiB，总量最多 40 MiB。
- 检查点只写入本机应用数据目录，不通过该功能上传云端；因为完整工程可能包含 Wi-Fi 密钥等内容，不能把该目录当作可公开同步的数据。
- “工程检查点”窗口显示时间、原因、积木数、板卡和大小；支持带危险确认的逐条删除，删除不会修改当前工作区、源码或已烧录固件；恢复板卡不同时先等待对应扩展加载，再走现有兼容加载与未知积木提示路径。

### 当前限制

- 滚动恢复闭环已完成：普通语义编辑约 12 秒防抖写入独立恢复稿，并比较恢复稿、磁盘工程和完整状态哈希后生成启动候选；不使用全局 `clean_shutdown` 标记。恢复当前工程前会再创建正式检查点，成功正式保存后清理对应恢复稿。
- 打开其他工程时若明确放弃未保存修改会先创建 `before_leave`；批量导入和安装第三方包前仍未自动建立检查点。
- 当前只显示快照元数据，不计算积木增删、字段变化或语义 diff。
- 如果恢复时缺少第三方积木包，未知积木保护层会保留原始序列化文本并进入只读模式，禁止覆盖保存、编译和上传；检查点不能替代对应包文件。
