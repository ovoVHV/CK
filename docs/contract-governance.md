# CK 合同版本治理

状态：Internal governance。更新时间：2026-08-25。

## 为什么必须单独治理

CK 的构建、证据、工具链和第三方包系统已经有多个独立合同。每个版本号都有历史原因，但如果继续为每个改动新建版本轴，就会出现“一个消费者接受 v4、另一个消费者要求 v5、第三个只看旧 contract hash”的合同爆炸。最终风险不是普通功能错误，而是安全门禁之间互相误判。

本文件是给实现者、审核者和 AI 修改代理的硬约束：**版本数量本身属于技术债，不得把新增版本当作默认实现手段。**

## 当前合同家族

版本号必须归属于一个明确的合同家族，不能脱离家族单独解释：

| 家族 | 当前入口 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| CK Forge | `ck-forge/v1` | 构建路由和回退边界 | 不定义证书字段或性能阈值 |
| 资格清单 | `ck_forge_qualified_targets.v1.json` / qualification schema | 候选目标和资格输入结构 | 不直接授予 Fast |
| NativeRelink 证书 | `ck-forge-native-relink-certificate.schema.json` | 本机证书结构、绑定和产物证据 | 不替代构建行为合同 |
| 构建行为 | Fast build contract | 命令图、对象复用和产物生成行为 | 不定义包质量报告 |
| 工具链身份 | toolchain identity schema | Core、编译器、工具和平台内容身份 | 不判断性能是否达标 |
| 性能策略 | performance policy | A/B 样本、速度门槛和 p95 规则 | 不改变证书数据结构 |
| 包质量报告 | quality report schema / ruleset | 第三方包结构、依赖、许可证和生成器门禁 | 不证明真板运行或作者身份 |

同一条数据只能有一个家族作为权威解释者。其他模块只能引用它的稳定字段和明确的兼容结果，不能复制一份“自己的版本判断”。

## 默认规则：扩展，不造新版本轴

1. 新需求先定位已有合同家族；能在现有字段中用向后兼容的可选字段、枚举扩展或附加证据表达，就不得创建新的独立 schema/contract/version 生命周期。
2. 证据格式和行为格式描述的是同一份不可分割的消费协议时，优先合并到所属合同家族，并在同一处定义校验顺序；不要让证书 vN、行为 vM 和 hash vK 各自决定是否可用。
3. 文案、日志字段、UI 展示、内部计时和实现重构不产生新合同版本。它们只要不改变消费者可观察的输入、输出、安全边界或复现结果，就不需要版本升级。
4. 版本升级只用于不兼容的机器可读变化：旧读取器无法安全解释、旧验证器会放行错误行为，或产物/安全边界改变且不能通过兼容扩展表达。
5. 新版本必须提供迁移或明确拒绝路径；未知未来 major/schema 必须 fail-closed，不能静默降级、借用相邻版本或根据名称猜测。
6. `contract_sha256` 只能证明某个合同内容的完整性，不能单独证明行为兼容。所有 hash 必须注明所属合同家族、输入范围和失效条件。

## 新版本决策门

任何拟新增版本号的改动，在合并前必须回答以下问题并写入变更记录：

- 现有哪个合同家族拥有这项数据和行为？
- 为什么现有字段、可选扩展或迁移无法表达？
- 这是规范兼容性、实现行为、证据格式、工具链身份还是性能策略变化？只能选择一个权威家族。
- 哪些消费者读取该合同？是否存在重复的本地版本判断？
- 旧版本是迁移、兼容读取，还是明确拒绝？拒绝时用户看到什么？
- 是否更新了 `docs/specification/README.md`、`docs/specification/index.json`、Schema、验证器、桌面端和 Node/Rust 测试？
- 是否搜索了旧版本字符串、contract hash、证书字段和过期条件，确认没有遗漏消费者？

如果不能回答，改动应先停在设计阶段，不得通过增加一个新版本号掩盖不清晰的责任边界。

## 修改顺序

1. 更新本文件中的合同家族归属和影响范围。
2. 修改唯一权威 Schema/策略/行为入口。
3. 更新 Specification 人类索引和机器索引。
4. 运行包 Schema、Specification、证书、路由和回归测试。
5. 重新生成受影响的证据；旧 EXE、旧 Core、旧工具链或旧 hash 只能标为历史，不能继续授权。
6. 在功能清单中记录用户可见边界，并检查安装包/诊断包是否仍携带正确合同版本。

## 给 AI 修改代理的提示

在修改 CK 构建或质量门禁前，必须先搜索：

```powershell
rg -n "schema_version|contract|contract_sha256|certificate|policy|toolchain|ruleset" docs scripts apps crates
```

先复用现有合同家族，再提出改动。禁止为了让一个测试通过而复制版本字段、放宽旧证书、跳过 hash/路径门禁或新增一个未登记的 `vN`。完成后必须在变更摘要中列出受影响的合同家族和需要重新生成的证据。
